# Partner handoff — proposed Gaming Station API v1

**For review, not evidence of implemented Padel House endpoints.** Contract
revision 0.1.0 is in `contracts/openapi.json`. Typed client interfaces derive from
that contract. No message has been sent to the partner and no agreement is claimed.

## Ownership and settings

The partner implements these in the existing Flask system:

1. Staff settings for billing start delay (including explicit zero), hourly rate,
   currency, billing unit/rounding and minimum charge. Validate allowed ranges;
   never treat zero delay as missing. PC and optional PS5 settings remain distinct.
2. Immutable per-session policy snapshots. Routine changes affect new sessions;
   explicit staff changes to an existing policy are audited and update its revision.
3. Cashier authorization for a station and one atomic pending/active session per PC.
4. An independent background scheduler for automatic paid start, with fresh valid
   game evidence. It cannot depend on the cashier browser remaining open.
5. All billable duration validation, rate calculation, rounding, cashier-only end,
   receipts and payment. The station cannot choose its price or paid start.
6. Station-scoped credentials, command queue, reconciliation and enforcement status.

The simulator will reproduce these responsibilities only for development. Suggested
policy record: `policy_version`, `billing_start_delay_seconds`, `hourly_rate_decimal`,
`currency`, `billing_unit_seconds`, `rounding_mode`, `minimum_charge_decimal`.
Use exact decimal arithmetic on the server. Partner must settle allowed rounding
values and minimum-charge semantics; no financial default is selected here.
These fields are deliberately absent from device write messages and UI controls.

## Endpoints and transport

All paths are relative to a configured `/gaming/v1` base. Production uses HTTPS.
The spec's loopback URL is a reserved simulator address, not a working API.

| Operation | Proposed path | Scope |
| --- | --- | --- |
| Enroll | POST `/devices/enroll` | One-use setup code |
| Renew/revoke self | POST `/stations/{station_id}/credentials/renew` or `/revoke` | This credential family only |
| Configuration | GET `/stations/{station_id}/configuration` | Station settings, no price controls |
| Authorization/session | GET `/stations/{station_id}/snapshot` | Current station only |
| Session read | GET `/stations/{station_id}/sessions/{session_id}` | History owned by this station |
| Heartbeat | POST `/stations/{station_id}/heartbeat` | Liveness, processes, restriction evidence |
| Launch request | POST `/stations/{station_id}/launches` | Expiring permit, one session |
| Cancel attempt | POST `/stations/{station_id}/launches/cancel` | Attempt only, never billing stop |
| Events | POST `/stations/{station_id}/events` | Durable raw observations |
| Commands | GET `/stations/{station_id}/commands?cursor=...` | Authenticated allowlisted restrictions |
| Results | POST `/stations/{station_id}/commands/results` | Verified/failed/rejected outcome |

Optional central catalog retrieval is deferred. The initial curated local catalog
uses the `GameProfile` schema. Central profiles can never bypass protected local
approval/installation validation. Staff/customer payment APIs are outside this contract.

## Authentication and wire envelope

Pairing codes are generated by authorized partner staff, short-lived, one-use and
bound to an intended station slot. Enrollment assigns the immutable UUID; labels
such as PC-01 are not credentials. Station count is configurable (initially 12).
`installation_id` must be regenerated for cloned installations before enrollment.

Proposed auth is an opaque per-station bearer access token and separately scoped
rotating renewal token. Enrollment/renewal have no bearer requirement but require
their own secret in the body. Use HTTPS, rate limits and strict schema validation.
Renewal works after access-token expiry while the renewal secret remains valid.
Rotation is atomic; replay with the same idempotency key/body returns the same
encrypted cached response. Revocation invalidates the entire credential family.
Staff revocation is partner-internal. The device may revoke only itself.
No token, secret, staff cookie or DB credential is exposed to React or logs.

Every request has API version and correlation ID; station writes contain station
UUID, UTC send time and session UUID when assigned. Before assignment it is null
where present; enrollment intentionally has no station UUID yet. GET requests
carry station/session scope in path and `X-Request-ID`. Responses carry server
time and echo the correlation ID. Event and command IDs are distinct durable UUIDs.
All applicable nested station/session IDs must match the authenticated scope.
Schema validation cannot replace these relational permission checks.

Session IDs identify financial lifecycles. `station_epoch` increases monotonically
for each fresh customer authorization; it never wraps/reuses an old value. Snapshot
revision orders station state, and session revision orders one session. Discard
older snapshots for current display, retaining history for audit only. An archived
session read reports that session's data and historical authorization/restriction
as-of its snapshot; it must not be installed as the current station snapshot.

## Core messages and example flow

Read `contracts/examples.json` for portable, schema-checked fictional JSON. The
fixture map names each schema and is suitable for a Flask implementation's input fixtures.
Its source is `contracts/examples.mjs`; regenerate using `npm run contract:generate`.
The example amount is invented for display-shape testing; it is not a venue rate.

| Message | Meaning |
| --- | --- |
| `authorizationGranted` / SnapshotResponse | Cashier-created authorization; Play still requires a launch request |
| `launchRequested` / LaunchRequest | Game ID and authorization; no price, deadline, command line or bill |
| `launchPermitted` / LaunchResponse | Server first-Play anchor, policy version, grace deadline, expiring attempt |
| `gameRunning` / GameRunningEvent | Observed configured process, linked to valid attempt/run |
| `launchFailed` / LaunchFailedEvent | No confirmed game; timeout/login/detection diagnostic |
| `gameExited` / GameExitedEvent | Process exit only; no session-ending authority |
| `stationUseObserved` / ObservedUseEvent | Raw cumulative segment duration; not billable duration |
| `sessionActive` / SnapshotResponse | Authoritative backend transition and paid duration |
| `cashierSessionEnded` / SnapshotResponse | Frozen bill, revoked authorization, enforcement pending |
| `restrictCommand` / RestrictCommand | Expiring station/session/epoch-bound action |
| `restrictionAcknowledged` / CommandResultRequest | Actual verified restriction or honest failure |
| `heartbeat` / HeartbeatRequest | Liveness and current process list; response refreshes snapshot/lease |

For a 20-second example policy, first Play at 12:00:00Z yields grace deadline
12:00:20Z. A running observation at 12:00:08Z can lead to paid start at 12:00:20Z
only if the game is still confirmed running and the attempt/authorization valid.
At 12:01:00Z the backend may report 40 billable seconds and the device may report
60 observed station-use seconds. Neither value substitutes for the other.

## Concurrency, retries and acknowledgements

Require `Idempotency-Key` on POST. Store canonical payload hash and result under
station+operation+key (enrollment under installation ID). Identical retry returns
the original response. Changed payload under the same key returns
`IDEMPOTENCY_CONFLICT` (409). Reconcile with a fresh snapshot after retry because
the cached response is historical. Never launch from an expired replayed permit.

Keep idempotency results at least through session termination plus seven days;
keep enrollment/renewal results through token validity. Keep durable event/command
dedup records with the retained session audit (proposed minimum 90 days, partner
to confirm). After cleanup, reject unknown old-session messages; never treat
forgotten historical IDs as a new financial action.

Under a database transaction/unique constraint, enforce one pending/active session
per station. Concurrent first requests with different keys reuse the existing
session; they cannot reset its first-Play anchor or apply another grace period.
Each attempt is individually expiring; superseding pending attempts invalidates
old attempts. In an active session, game switching does not change paid start.
In-flight command and new-authorization races must be fenced by station epoch.

Retry network failures, 429 and retryable 503 with exponential backoff and full
jitter (1 second base, 30 seconds cap; honor a longer Retry-After), stable body/key,
and no extension of authorization validity. Stop launching on 401, try one eligible
renewal, then require protected re-pairing on revoked/expired renewal. Reconcile
409/410 before a new action. Do not retry 400/403 blindly. Persist unresolved work.

Events are at-least-once. Return one result per supplied event: accepted, duplicate,
rejected or retry. Accepted/duplicate are terminal acknowledgements; rejected is
quarantined with a code for diagnostics. Retry/omitted acknowledgements remain in
the outbox. Mixed batches may return HTTP 200 with per-event results. A structural
or scope-invalid batch returns 400/403 with no partial acceptance.

An event UUID identifies immutable bytes; reuse with changed contents is rejected.
Sequence is monotonically increasing within station+OS boot+event stream, persisted
across agent restarts. Heartbeats use a separate sequence stream. Out-of-order
events are stored/deduplicated, but cannot roll state backward or revive a stopped
run. Maintain each attempt/run's high-water sequence and terminal tombstones.
A running event delivered after a higher-sequence exit is historical evidence only.
Cumulative duration is reconciled by session/boot/segment high-water value, never
summed per report. Reject decreasing/conflicting values; flag discontinuities.

## Timing validation and automatic transitions

Use server time for accepted first Play, deadline, cashier end and snapshot time.
For process confirmation, record receipt time, observed UTC time, monotonic offset,
boot identity and sequence. In v1 use server receipt time as the confirmation anchor
unless a continuous, authenticated time-correlation interval proves an earlier
observation. Never backdate across unverified/offline/reboot gaps. A delayed
historical observation cannot newly activate a cancelled or expired attempt.

Heartbeat cadence must be shorter than the configured evidence freshness window
and shorter than active authorization renewal window. The server checks positive
timing configuration consistency rather than accepting impossible combinations.
At grace, the scheduler requires fresh running evidence for the current valid
attempt, no superseding exit/cancel/failure, and current authorization. If evidence
has become stale, defer to reconciliation rather than assume continued play.
At actual transition the game must still be running. Expiry does not become valid
again merely because a delayed event claims an earlier local timestamp.

Update immutable policy snapshots only through audited staff actions with explicit
semantics. A station event cannot change settings, paid start, rate or end time.
The device sees grace timestamps and backend display amounts, not a billing algorithm.

## Command delivery and assignment safety

Commands originate in authenticated station-scoped HTTPS responses. No additional
command signature format is invented for v1; a future offline transport would need
its own authenticity design. Persist commands/results in service-owned storage.
The allowlist initially contains only `restrict_station` with locally supported
profiles. No shell, arbitrary URL, download or uploaded script is allowed.

GET command polling is not acknowledgement. Redeliver until a terminal result or
expiry, even if a cursor advances. Expired unresolved commands leave enforcement
pending/failed and station unavailable; the backend can issue a fresh command ID
for the same ended session. Match station/session/epoch/revision and validate expiry
before side effects. Cache results for duplicates. A verified result requires
restricted state, non-null verification time and evidence; reject contradictions.
Failure/expiry/unsupported/stale outcomes must not be counted as success.

Cashier stop must atomically freeze end/price, revoke the authorization lease and
queue enforcement. Station reassignability requires enforcement resolution and
explicit staff authorization. Do not reassign solely because `session.state` is
ended. PC offline status must be visible in the cashier dashboard; the bill is
frozen even when enforcement cannot yet be confirmed.
