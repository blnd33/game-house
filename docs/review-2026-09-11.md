# Review and completion work after the Phase 3 changes

The existing Phase 2 interface and Phase 3 catalog/detection work were retained.
The owner's sequencing decision overrides the original phase gate order: finish
the local system first, and verify real games individually afterward.

## Gaps found and addressed

- Phase 3 did not compile: the development panel invocation lacked its required
  prop. Fixed while retaining the UI.
- Native catalog launches had no backend permit boundary. An unpaired/unapproved
  agent now denies them; expiring permits come from the station API.
- Sample cashier controls could drive a native launcher. Sample mode is now an
  explicit separate build and normal/native operation uses agent state only.
- No independent persistent backend existed. Added a loopback SQLite-backed
  development server, policy snapshots, automatic scheduler and protected CLI.
- Monitoring events disappeared when the UI disconnected. Added SQLite outbox,
  stable event/batch IDs, terminal acknowledgements, persisted session snapshots,
  cumulative observation segments and encrypted enrollment/renewal retry records.
- Agent networking needed real API validation and credential handling. Added
  configured HTTPS/explicit loopback transport, generated-schema validation,
  station-scope checks and DPAPI credentials.
- Local pipe server identity and venue hosting were unfinished. Added Windows
  Service hosting, restricted player-SID pipe ACLs, client executable checks and
  a production relay validating the server PID through SCM.
- A failed executable spawn incorrectly returned `ok: true`. It now returns a
  failure. Missing process start identity no longer counts as reliable evidence.
- Missing leases and failed restrictions could leave Play enabled in the UI.
  Both now deny Play; catalog refreshes after reconnection.
- UI restarts could kill the development agent. It now runs independently.
- Offline enforcement could be delayed by HTTP backoff. An independent monotonic
  watchdog checks the authorization deadline without waiting for the HTTP lock.
- Restriction, installation and update scaffolding were missing. Added a
  disabled-by-default WTS disconnect/verify profile, versioned development package,
  signed-manifest support, integrity-only dry run, idle-update guard and rollback
  activation procedure. No real installation or restriction has been exercised.

## Concrete limitations requiring later environment checks

The package is a development release. Production service/relay ACLs, restriction
and recovery must be verified on an authorized target PC. The WTS profile must be
paired with a staff-controlled reconnect credential; test pre-Play access and
leftover game windows. The code does not implement a new Windows shell or claim
that fullscreen Electron prevents bypass. Game closure/account cleanup stays
deliberate, and failed enforcement must keep the station unavailable.

The backend simulator chooses conservative recovery: after a missed authorization
window or a new agent monitoring epoch, hold the station for staff. It does not
silently continue billing unverified powered-off gaps. The partner must agree to
the recovery policy before real integration. The simulator uses Node's currently
experimental SQLite module only in development; the native agent uses Microsoft.Data.Sqlite.

The device API adapter is implemented, but no real partner endpoint, enrollment,
policy change or receipt has been tested. API agreement remains deferred by the
owner. Signing identity, update distribution, venue account setup, artwork and
actual games remain external inputs. PS5 automation remains out of scope.
